# Wed Shot 技術決策記錄(ADR)

依時間順序記錄關鍵決策、被否決的方案與否決原因。
許多結論來自在真實 Chrome 上的實測(ASUS 產品頁,文件高度 10909px)。

---

## 1. 形態:DevTools 面板 → 獨立工作頁

- **v1** 做成 F12 開發人員工具面板(`devtools_page`)。
- **決策**:改為點擊工具列圖示開啟獨立分頁(`action.onClicked` → `panel.html?url=…`)。
- **理由**:使用者要的是獨立工具,不是 DevTools 的附屬面板;
  且 DevTools 頁面的 chrome.* API 受限,獨立擴充頁擁有完整 API。

## 2. 畫面來源:靜態截圖 → 即時 iframe(wedview)

- **否決**:先擷取一張靜態截圖再框選 —— 無法互動、無法反映動態內容。
- **決策**:以 iframe 內嵌目標網頁,`declarativeNetRequest` session 規則
  移除 `X-Frame-Options` / CSP 標頭,規則以 `tabIds` 限定只影響本分頁。
- **代價**:frame-busting 網站仍可能拒絕顯示;可接受。

## 3. 區域擷取方案演進(本專案最曲折的一條線)

| 方案 | 結果 | 否決原因 |
| --- | --- | --- |
| `captureVisibleTab` 拍工具頁再裁切 | ✗ | 對 `chrome-extension://` 頁面**沒有權限**(實測報錯);且解析度受顯示縮放影響 |
| 捲動拼接(分段捲動 + 多次擷取) | ✗ | `captureVisibleTab` 每秒 2 次硬限制;**動態元件**(sticky、輪播、動畫)在分段間移動造成接縫 —— 使用者明確否決 |
| debugger 附加 **iframe target** 直接截圖 | ✗ | 實測 CDP 回覆 `Command can only be executed on top-level targets`;另 `getTargets()` 的 iframe target **不帶 tabId**,以 tabId 過濾會默默找不到目標 |
| debugger 附加工具頁 + `captureBeyondViewport` 拉高 iframe 一次成像 | ✗ | 兩個問題:(a) OOPIF 在**真實視窗外的部分不會被點陣化**(拍到全白,Chromium 已知限制);(b) 拉高視窗令 vh 版面位移(實測文件 10909→12989px),框選位置失準 |
| `Emulation.setDeviceMetricsOverride` 擴大視埠再拍 | △ | 能解 OOPIF 點陣化,但模擬啟動瞬間整頁跳動,體驗差 |
| **最終方案**:所見即所得 —— 不動版面、`clip` 取目前畫面上的框選區、`scale = 1/zoom` 重新點陣化 | ✓ | 框選是在螢幕上拖出來的,必然在可視範圍內 → 不需模擬、零抖動;`scale` 讓 Chrome 以高解析度重繪,輸出 1:1 與顯示縮放無關 |

視埠模擬保留為極端狀況(clip 超出視窗)的保險,觸發條件以 **clip** 而非整個 stage 判斷。

**要擷取更長的內容 → 把「尺寸」高度調大**:預覽與擷取共用同一份版面,
完全一致,無拼接、無 vh 位移。這是與「網頁只該看到 960×960」的取捨,
實測後採用一致性優先。

## 4. 文件座標選取 → 版面座標(WYSIWYG)

- 曾實作以文件座標追蹤框選(捲動時起點跟著內容移動、拖到邊緣自動捲動)。
- **否決原因**:配合捲動擷取時,sticky 標頭會被「搬進」非其所在的區域;
  且擷取結果與預覽不一致。
- **決策**:框選、擷取一律以目前畫面(版面座標)為準 —— 拍到的就是看到的。

## 5. 浮動元件隱藏

- 需求:截圖只要內容本身,sticky 標頭(如產品副導覽列)不入鏡。
- **決策**:擷取瞬間由 content script 將 `position: fixed` 元件一律
  `visibility: hidden`;`position: sticky` 元件只在頁面**已捲動**時隱藏
  (未捲動時 sticky 在自然位置,屬於內容)。拍完還原。

## 3.1 擷取後「卡住、放大的網頁蓋住面板」:視窗化的顯示殘影

- 回報:尺寸 1800×2800,拍完第一張後一段時間無法框選,「整個網頁放大殘留、
  蓋住擴充的操作」,過一陣子又恢復。**全螢幕不會,視窗化才會**(使用者實測)。
- **根本原因**:`clip.scale = 1/zoom` 的擷取會讓 Chrome 暫時以高倍率重繪、
  畫面撐得比視窗大。視窗化時,Windows 會把那張放大的舊畫面一直留在視窗上,
  直到顯示區重設(例如調整視窗大小)才換回來。
- 實機紀錄佐證(使用者在測試視窗中重現,背後以 CDP 記錄):
  - 每個滑鼠事件的處理延遲都只有 0–5ms,沒有長任務,網頁與面板**一直都是活的**;
  - 但使用者是對著「看到的舊畫面」拖的,面板收到的座標落在灰色區、
    夾回舞台邊緣後寬度為 0 → 不擷取,看起來像卡住;
  - 每次恢復前都剛好調整過視窗大小;在卡住當下把視窗寬度 +1px 再改回,立刻恢復。
- **決策**(已於 §9 移除:擷取一律 100%、clip 不帶縮放,殘影不再發生):每次擷取後(`debuggerCapture` 的 `finally`),以 Wed Shot 自己的偵錯連線
  `Emulation.setDeviceMetricsOverride` 設成**和目前完全相同**的尺寸與 DPR,50ms 後清除。
  使用者實機確認可立即恢復;尺寸沒變,所以版面不重排、視窗也不動。
- 否決的做法:
  - 拍完把視窗寬度 ±1px:有效,但整個視窗會抖,使用者否決。
  - 拍完補拍一張不裁切、不縮放的普通截圖:實機無效。
- 排查期間依錯誤假設加過、後來**移除**的程式(皆非成因):
  擷取鏈各 await 的逾時保護(`withTimeout`)、
  網頁上圖片原生拖放轉框選(`dragstart` 攔截)與面板全域取消 `dragstart`。
  畫面內不按 Ctrl 拖圖片,仍是瀏覽器原本的拖曳行為(網頁模式)。
- 附帶觀察(未處理):輸出寬度偶有 1–4px 的落差(例 1785 → 1781~1784),
  推測是 clip 以 CSS px × zoom 後被取整到裝置像素所致。

## 5.1 截圖排除頁面捲軸

- 需求:截圖不要拍到內嵌頁右側/下方的捲軸。
- **否決**:擷取瞬間以 CSS(`scrollbar-width: none` / `::-webkit-scrollbar`)
  把捲軸藏掉 —— 捲軸佔版面寬度,一藏內容就重排(版面橫向撐開 ~15px),
  違反「零抖動 + 所見即所得」兩條主線。
- **決策**:content script 以 `innerWidth − documentElement.clientWidth`
  (高度同理)回報捲軸尺寸,工具頁把**可框選範圍**縮成
  `shotW = stageW − sbW`、`shotH = stageH − sbH`;
  clamp 與成像 clip 共用同一上限 → 選不到捲軸、也拍不進捲軸,版面完全不動。
- 捲軸可能在載入後才出現/消失,故 `wedshot:hidefixed` 的回應順便帶回最新尺寸,
  每次擷取都以當下數值夾範圍。
- **限制**:content script 被擋掉的頁面回報不到尺寸(視為 0,行為同從前);
  覆蓋式捲軸(overlay scrollbar)不佔版面,量得 0、無從裁掉。

## 5.2 直接開圖片網址:改寫 Chrome 圖片檢視頁

- 問題:使用者得先知道原圖寬度、再把「尺寸」調到一樣,才拍得到滿版圖。
- 實測(iframe 載入 400×300 PNG)釐清了成因:**Chrome 在 iframe 裡不會 shrink-to-fit**
  ——「寬高都塞進視窗」只在頂層分頁生效。iframe 寬 260 時圖仍是 400×300、
  貼左上角、長出兩條捲軸。
- **決策**:content script 偵測 `document.contentType` 為 `image/*`(排除 SVG:
  那是 SVGDocument,沒有 `<img>`)時注入樣式表:白底、
  `img { display:block; margin:0 auto; max-width:100% !important; width/height:auto !important }`。
  → 畫面寬 < 圖片寬:縮到剛好滿寬(實測 260×195、捲軸消失、上下置中 top=33);
    畫面寬 > 圖片寬:原尺寸、水平置中(實測 left=143 正好置中)、**不放大**;
    fit 後仍比畫面高的長圖(實測 400×900 → 245×551)可完整捲到底,無死角。
- `!important` 是必要的:檢視頁把樣式寫在 `<img>` 的內嵌樣式上(點擊放大也是改它)。
- 置中用 `flex + min-height:100vh + align-items/justify-content: safe center`:
  `safe` 是關鍵 —— 圖比畫面高時,一般的 `center` 會把溢出的部分推到捲不到的上方。
  曾為了「加快」簡化成 `margin: 0 auto`(只水平置中),但實測確認慢的是**時機**
  而非版面計算,故改回雙軸置中。img 的 margin 歸零,置中一律交給 `safe center`
  (auto margin 沒有 safe 行為)。
- **時機**:原本等 `hello` 才套,而 `hello` 發在 iframe 的 `load` 之後
  (大圖=整張下載完),會先閃一次原尺寸。改為 `run_at: document_start` +
  `location.ancestorOrigins[0]` 同步比對本擴充 origin —— 認出是工具頁內嵌就當場套,
  樣式先進場、`<img>` 之後解析出來照樣套得到。認不出時仍退回 hello 那條路,
  一般瀏覽分頁的圖片不受影響。

## 6. 操作模式:切換按鈕 → 手勢偵測

- **否決**:「拖曳選取」開關按鈕(多一步、易忘記切換)。
- **決策**:預設網頁模式;按住 Ctrl = 拖曳模式(十字游標);
  畫面外(灰色區)起手 = 自動拖曳模式。
- **關鍵限制**:跨網域 iframe 的滑鼠事件父頁收不到,
  畫面內的 Ctrl+拖曳必須由 content script 攔截並轉發座標;
  Ctrl 游標亦需雙向同步(焦點在誰身上就由誰偵測、通知對方)。

### 6.1 框選中鎖住捲動

- 需求:框選進行中不要捲動頁面 —— 框選是版面座標,網頁一捲,框住的內容就換了。
- 滑鼠在網頁上時,滾輪事件進的是 OOPIF,工具頁攔不到 → 由 content script 擋:
  網頁內 Ctrl 起手的框選(`fwdDragging`)直接擋;灰色區起手的框選由工具頁在
  `beginDrag` / `endDrag` 送 `wedshot:scrolllock` 開關。滑鼠在灰色區時由工具頁自己擋。
  Ctrl+滾輪仍是縮放。

## 7. 儲存方案演進

| 方案 | 否決原因 |
| --- | --- |
| `showDirectoryPicker` 選資料夾 + 檔名前綴設定 | 檔名無法在存檔當下輸入 |
| `window.prompt` 輸入檔名 → 資料夾 | 兩段式,體驗差 |
| 每張各跳一次另存對話框 | 多張時對話框轟炸 |
| 第一張另存 + 其餘程式接續寫入同資料夾 | `chrome.downloads` 只能寫入「下載」資料夾底下;位置在外時行為分裂,且需探測下載根目錄等髒手段 |
| **最終方案**:單張另存 PNG;多張打包 ZIP 一次另存 | ZIP 是單一檔案 → 存哪都行、只輸入一次檔名 |

- ZIP 內部檔名要跟隨輸入 → **先** `showSaveFilePicker` 拿到檔名、**再**打包,
  內部即 `檔名 (1..n).png`(依選取順序)。
- ZIP 為自製 STORE 打包器(CRC-32 + UTF-8 旗標,無外部相依),
  已用系統解壓驗證正確性。
- 曾留一段「不支援 picker 就退回 `chrome.downloads`」的備援,後來**刪除**:
  桌面 Chrome 一律支援,該分支是永不執行且未經驗證的死碼
  (且它對單張用 `data:` URL,MV3 下載器未必吃);`downloads` 權限一併移除。
  真正會失敗的是政策封鎖寫入(丟 `NotAllowedError`,不是 `AbortError`),
  那種情況直接回報錯誤,不假裝有備援。

### 7.1 存檔通知:繞了一圈,回到另存 + 系統通知

- 回報:「儲存沒有跳下載通知蠻奇怪的」—— `showSaveFilePicker`
  (File System Access API)是**直接寫檔**,不經 Chrome 下載器,
  所以沒有下載氣泡、也不會出現在 `chrome://downloads`,存完只剩狀態列一行字。
- 期間曾整個改用 `chrome.downloads`(`saveAs: true` + blob URL)換到真正的
  下載通知,但代價是 **ZIP 內部檔名不能再跟隨對話框輸入的檔名**
  —— 打包必須在對話框之前完成,下載器只在事後才知道最終檔名。
  試用後**否決**:內部命名比下載清單重要。
- 以下組合逐一評估後都不可行:
  - picker 拿檔名 + 下載器再存一次 → **兩份檔案**
    (`chrome.downloads` 的 `filename` 只能相對於「下載」資料夾,
    絕對路徑與 `..` 會被拒;`FileSystemFileHandle` 也不露出完整路徑)。
  - picker 拿檔名 + 下載器 `saveAs: false` 不跳窗 → 檔案一律落在下載資料夾,
    picker 選的位置形同白選。
  - 把既有檔案補登進下載清單 → **無此 API**。
- 也試過以 `chrome.notifications` 自行跳系統通知補位,同樣**否決**:
  那不是下載氣泡、也進不了下載清單,只為此多要一個 `notifications` 權限不值得。
- **決策**:維持 `showSaveFilePicker`,完成訊息就留在狀態列。
  「存檔沒有下載通知」是 File System Access 的本質,不是可調的設定。
- 後續:存檔成功改為**清掉勾選** + 片段欄中央「轉圈 → 打勾 → 自動淡出」。
  中間試過需按「確定」的 `<dialog>`,否決:每存一次都要多按一下。
  進度圈為純 SVG + CSS(`stroke-dashoffset` 畫弧與勾),不需任何權限。

## 8. 偵錯提示列(debugger infobar)緩解

- `chrome.debugger` 是唯一能對擴充頁成像的 API(見決策 3),
  Chrome 強制顯示「已開始偵錯」提示列,擴充功能無法移除。
- 演進:每次擷取附加/拆除(提示列反覆彈出收回、版面跳動)
  → 附加後**常駐**(只出現一次)→ **開頁即附加**(操作前就佔好位,之後零跳動)
  → 提示列是**瀏覽器全域**的(所有視窗都顯示,開新視窗無法隔離)
  → 依分頁可見性附加/拆除:工具頁前景才附加,退背景即拆除,
  逛其他網頁時不再看到提示列。
- 配套:批次列加高(被擠壓也點得到);
  桌面捷徑「Chrome (Wed Shot)」帶 `--silent-debugger-extension-api` 旗標,
  可徹底不顯示提示列。
- `onDetach`(使用者按提示列「取消」)→ 標記失效,下次擷取自動重附加。

## 9. 顯示縮放與輸出解析度脫鉤

- 顯示預設「自動」fit 進面板(縮多小都行),純視覺;
- 輸出固定 1:1(原本用 CDP `clip.scale = 1/zoom`,見下方已改為擷取瞬間切 100%),
  曾被質疑「100% 又回來了」—— 實際指擷取瞬間的版面跳動(capfull 模式),
  已改為完全不動版面,保留 1:1 輸出。
- **縮放顯示時擷取模糊**(使用者回報:自動縮放下糊、手動 100% 清楚):
  內嵌網頁是跨程序的 OOPIF,只會以畫面上的縮小尺寸點陣化。
  `clip.scale = 1/zoom` 只是把那張小點陣放大,文字、圖片都糊。
  上面「`scale` 讓 Chrome 以高解析度重繪」對 OOPIF **不成立**。
  以獨立 Chrome + `?devhook=1` 實測(960×960,清晰度=相鄰像素差平均):
  | 做法 | 69% | 50% | 100% | 125% |
  | --- | --- | --- | --- | --- |
  | 原本 `clip.scale = 1/zoom` | 33 | — | 58* | 49 |
  | 同尺寸視埠、`deviceScaleFactor = DPR÷zoom`(等 0.3–2.5 秒) | 33–35 | — | — | — |
  | **擷取瞬間畫面一律 100%** | 57.6 | 57.6 | 57.6 | 57.6 |

  \* 舊路徑 100% 的 58 偏高是假象:畫面比視窗高時擴大視埠,畫面仍在面板捲動區內,
  **底部 18px 拍進了工具自己的狀態列**(多出的文字邊緣墊高了數值)。
  - 放大(125%)時 `clip.scale = 0.8` 是把 125% 的點陣縮回去,重新取樣變軟。
  - 否決:連拍等圖片重新解碼(錯誤假設:第一張就與第二張完全相同)、
    調高 DPR 模擬(OOPIF 不跟著重繪)。兩者實測無效,已移除。
  - **決策**:縮放不是 100%、或框選超出視窗時,擷取瞬間把 `.stage` 設成
    `position: fixed` 釘在視窗左上角、最上層,縮放時再加 `transform: none`
    (不佔版面,面板配置不動;網頁 CSS 尺寸不變,不重排)。
    仍超出視窗時沿用視埠模擬,單拍(`clip.scale = 1`)後還原 `cssText`。
    各縮放輸出逐像素一致(只有縮放顯示的點陣圖片有 ±1/255 的取樣捨入差)。
  - clip 不再帶縮放 → 不會產生 §3.1 的殘影,`refreshViewSurface` 已整段移除,
    每次擷取少閃兩下。
  - **代價**:縮放不是 100% 時,擷取的瞬間畫面會閃一下 100% 的樣子。
    畫質優先,這個代價可以接受(與本節前段的「零抖動」取捨相反)。

(原生圖片拖曳會吃掉點擊);尺寸輸入框 focus 全選。

## 11. 測試方法

- 瀏覽器自動化工具**無法操作其他擴充功能的頁面**(截圖/注入/點擊全被拒),
  故以 `?autotest=1` 內建自測:結果寫入 `document.title`,外部輪詢分頁標題。
- 截圖內容以像素統計驗證(非白比例 ink%、量化顏色數),避免「拍成功但全白」誤判。
- 清晰度比對(§9):以獨立設定檔啟動 Chrome(`--remote-debugging-pipe
  --enable-unsafe-extension-debugging`),CDP `Extensions.loadUnpacked` 載入 `dist/`,
  開 `panel.html?devhook=1&url=<本機測試頁>`,再以 `Runtime.evaluate` 呼叫
  `__wedshot.capture(zoom)` 取回影像;各縮放結果以清晰度數值與逐像素比對驗證。
  測試 Chrome 要加 `--headless=new`:有視窗時使用者的滑鼠會干擾模擬輸入。
- CDP `Input.dispatchMouseEvent` 的限制:灰色區按下、在網頁(OOPIF)上放開時,
  模擬的放開事件不會送到持有 pointer capture 的工具頁,框選停在進行中;
  真實滑鼠正常(使用者實機確認),屬模擬輸入的假象,不需修正。
- 未封裝擴充的 ID 可由**資料夾絕對路徑的 SHA-256** 推算(前 16 bytes 映射 a-p),
  用於在無法讀取 chrome://extensions 時定位擴充頁網址。
- 其他實測教訓:分頁退背景會被 Chrome 凍結(計時器停擺,測試假死);
  `navigate` 類工具會把 `chrome-extension://` 協定改壞,需以
  web_accessible_resources + 頁內 `location.href` 導航;
  content script 更新必須重載擴充功能才生效。
